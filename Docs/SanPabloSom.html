Documentación Técnica y Funcional del Proyecto

Proyecto: Sistema de Gestión de Acompañamiento Terapéutico

Cliente / Entidad: Centro Terapéutico San Pablo

Objetivo: Automatizar la gestión de pacientes, asignación de profesionales sombra y registro de bitácoras e historias clínicas.

1. Visión General y Roles del Sistema

El sistema implementa un control de acceso basado en roles (RBAC):

  • Administrador (Rol 1): Encargado de gestionar usuarios, crear fichas de pacientes, asignar profesionales sombra a pacientes específicos y supervisar las bitácoras registradas.
  • Profesional Sombra (Rol 2): Encargado de consultar los pacientes que tiene asignados y diligenciar los reportes diarios de evolución (historias clínicas / bitácoras) al finalizar cada sesión.

2. Requerimientos del Sistema

Requerimientos Funcionales (RF)

ID Módulo Descripción
RF-01 Autenticación El sistema debe permitir el inicio de sesión a usuarios activos mediante su documento_identidad y contraseña, redirigiéndolos a su módulo según rol_id.
RF-02 Gestión de Pacientes El Administrador debe registrar, actualizar y consultar los datos demográficos y de acudientes de los pacientes.
RF-03 Asignación de Plan Sombra El Administrador debe poder vincular a un Profesional Sombra con un Paciente, registrando la fecha de inicio, fecha fin estimada y los objetivos del plan.
RF-04 Registro de Bitácoras El Profesional Sombra debe diligenciar la bitácora diaria de acompañamiento indicando resumen de la jornada, conductas observadas y alertas.
RF-05 Control e Historial El Administrador y el Profesional Sombra (solo para sus pacientes asignados) deben poder consultar el historial acumulado de reportes diarios.

Requerimientos No Funcionales (RNF)

  • RNF-01 (Seguridad & RBAC): Restricción de acceso a nivel de backend para evitar que un profesional consulte información de pacientes no asignados a su perfil.
  • RNF-02 (Arquitectura Modular): Separación clara entre el punto de entrada público (public/), la lógica de negocio (controllers/), las reglas de datos (models/) y las vistas (modules/).
  • RNF-03 (Usabilidad Móvil): La interfaz para el registro de bitácoras debe ser fluida para permitir el diligenciamiento desde tablets o dispositivos móviles en campo.

3. Historias de Usuario (HU)

HU-01: Autenticación por Documento de Identidad

Como: Usuario del sistema (Admin / Profesional).

Quiero: Iniciar sesión ingresando mi número de documento y contraseña.

Para: Acceder al panel correspondiente a mis permisos.

Criterios de Aceptación:

  • Validar credenciales contra la tabla usuarios usando documento_identidad.
  • Permitir el acceso únicamente si estado = 'activo'.
  • Guardar los datos del usuario en sesión (id, nombre, rol_id).
HU-02: Asignación de Profesional a Paciente

Como: Administrador del Centro San Pablo.

Quiero: Crear una asignación vinculando un paciente_id con un profesional_id y definiendo los objetivos del acompañamiento.

Para: Establecer formalmente el inicio del servicio del profesional sombra.

Criterios de Aceptación:

  • Desplegar solo profesionales activos (rol_id = 2) y pacientes en estado 'activo'.
  • Registrar el estado inicial de la asignación como 'activo'.
HU-03: Diligenciamiento de Bitácora / Reporte Diario

Como: Profesional Sombra.

Quiero: Registrar la información diaria del acompañamiento terapéutico realizado a mi paciente asignado.

Para: Dejar evidencia del proceso de avance y novedades observadas.

Criterios de Aceptación:

  • El profesional solo ve las asignaciones activas vinculadas a su id.
  • El campo resumen_jornada es obligatorio.
  • La fecha y hora (fecha_registro) se asignan automáticamente al guardar.

4. Estructura de la Base de Datos (`sanpablo_bd`)

CREATE DATABASE IF NOT EXISTS sanpablo_bd;
USE sanpablo_bd;

-- 1. Tablas Core: Roles y Usuarios
CREATE TABLE IF NOT EXISTS roles (
    id INT AUTO_INCREMENT PRIMARY KEY,
    nombre VARCHAR(50) NOT NULL UNIQUE
) ENGINE=InnoDB;

CREATE TABLE IF NOT EXISTS usuarios (
    id INT AUTO_INCREMENT PRIMARY KEY,
    rol_id INT NOT NULL,
    documento_identidad VARCHAR(30) UNIQUE,
    nombre VARCHAR(100) NOT NULL,
    apellido VARCHAR(100) NOT NULL,
    email VARCHAR(150) NOT NULL UNIQUE,
    password_hash VARCHAR(255) NOT NULL,
    telefono VARCHAR(20),
    estado ENUM('activo', 'inactivo') DEFAULT 'activo',
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    FOREIGN KEY (rol_id) REFERENCES roles(id) ON DELETE RESTRICT ON UPDATE CASCADE
) ENGINE=InnoDB;

-- 2. Pacientes
CREATE TABLE IF NOT EXISTS pacientes (
    id INT AUTO_INCREMENT PRIMARY KEY,
    documento_identidad VARCHAR(30) UNIQUE,
    nombre VARCHAR(100) NOT NULL,
    apellido VARCHAR(100) NOT NULL,
    fecha_nacimiento DATE NOT NULL,
    nombre_acudiente VARCHAR(150),
    contacto_acudiente VARCHAR(50),
    observaciones_iniciales TEXT,
    estado ENUM('activo', 'inactivo', 'finalizado') DEFAULT 'activo',
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
) ENGINE=InnoDB;

-- 3. Asignaciones (Relación Profesional - Paciente)
CREATE TABLE IF NOT EXISTS asignaciones_plan_sombra (
    id INT AUTO_INCREMENT PRIMARY KEY,
    paciente_id INT NOT NULL,
    profesional_id INT NOT NULL,
    fecha_inicio DATE NOT NULL,
    fecha_fin DATE NULL,
    estado ENUM('activo', 'pausado', 'finalizado') DEFAULT 'activo',
    objetivos_plan TEXT,
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    FOREIGN KEY (paciente_id) REFERENCES pacientes(id) ON DELETE CASCADE ON UPDATE CASCADE,
    FOREIGN KEY (profesional_id) REFERENCES usuarios(id) ON DELETE RESTRICT ON UPDATE CASCADE
) ENGINE=InnoDB;

-- 4. Historias Clínicas / Reportes Diarios
CREATE TABLE IF NOT EXISTS historias_clinicas_reportes (
    id INT AUTO_INCREMENT PRIMARY KEY,
    asignacion_id INT NOT NULL,
    fecha_registro DATETIME DEFAULT CURRENT_TIMESTAMP,
    resumen_jornada TEXT NOT NULL,
    comportamiento_observado TEXT,
    novedades_alertas TEXT,
    FOREIGN KEY (asignacion_id) REFERENCES asignaciones_plan_sombra(id) ON DELETE CASCADE ON UPDATE CASCADE
) ENGINE=InnoDB;
